# Форма за запитване: работа, защита и проверки

Последна промяна: **8 октомври 2026 г.**  
Версия на сайта: commit `4a717d6`

## Предназначение и файлове

Формата на `/kontakti/` изпраща запитвания към `office@vamo.bg` чрез PHP на същия хостинг. HTML е в `src/components/ui/ContactForm.astro`, обработчикът е `public/kontakt.php`, а страницата за успех е `/thanks/`. `public/kontakt.php` влиза в статичния build и се качва автоматично при push към `main`.

## Какво беше поправено

Преди промяната JavaScript изчисляваше дневен токен, а PHP отхвърляше всяка заявка без него. Човек със спрян JavaScript попадаше на страница „Благодарим“, въпреки че запитването не беше доставено. Грешките след сървърна валидация се показваха само чрез JavaScript на статичната контактна страница.

Сега HTML формата работи и без JavaScript. Липсващият токен и timestamp не блокират подаването. Невалиден **подаден** токен, линк в съобщението и необичайно бързо подаване маркират писмото с `[ЗА ПРОВЕРКА]`, но не губят запитването. Токенът е публичен сигнал, а не удостоверяване или CSRF защита.

## Обработка на POST

1. PHP допуска само `POST`; друг метод получава 405.
2. Попълнено скрито honeypot поле се логва и отхвърля без имейл. Това е единственият автоматичен тих отказ.
3. PHP проверява съгласието, задължителните име и телефон, формата на незадължителния имейл и дължините на полетата.
4. Невалидни данни връщат HTML страница с HTTP 422, ясно съобщение и безопасно екранирани попълнени стойности. Страницата има собствена форма за повторен опит и не се нуждае от JavaScript.
5. След валидиране се прилага лимит от **10 запитвания за един IP адрес за последния час**. Броячът се пази в `vamo-private` извън публичния корен и се обновява под `flock`. При достигане на лимита отговорът е видим HTTP 429.
6. Запитването се изпраща по имейл и независимо се записва в `zapitvaniya.jsonl` в частната папка. Ако и двете действия се провалят, потребителят вижда HTTP 503, а не фалшиво потвърждение.
7. Потвърждение на подателя се изпраща само ако е оставил имейл и заявката няма подозрителни флагове.
8. Успехът води с HTTP 303 към `/thanks/`, така че опресняване на страницата не подава формата отново.

Адресът на подателя не се поставя в `From`; използва се домейнът на VAMO, а валидният клиентски имейл влиза в `Reply-To`. Не се използва външна услуга или нов PHP ендпойнт.

## Защита и ограничения

Honeypot, сървърна валидация, лимит по IP и маркиране на съмнителни заявки ограничават масовия спам. Публичният дневен токен не може да спре бот, който изпълнява или имитира JavaScript. Лимитът по IP може да засегне много хора зад една обща мрежа; затова връща видимо съобщение с алтернативен контакт. Ако частната папка не е достъпна, лимитът не може да се наложи — това трябва да се наблюдава на хостинга. Обработчикът не пази състояние за еднократно използване на всяка валидна заявка; 303 предотвратява повторно изпращане чрез refresh на страницата за успех, но не и умишлен нов POST.

Текущата страница за грешка е самостоятелен PHP HTML изглед. Тя запазва важните полета, но не използва общите Astro header и footer. Това е следствие от статичния сайт и избягва зависимост от JavaScript при грешка.

## Извършени проверки

- `php -l public/kontakt.php` — без синтактични грешки.
- `npm run check`, `npm run build`, `npm run check:sitemap` — успешни.
- Локален PHP сървър с изключено реално изпращане на поща: невалиден имейл връща 422 и запазено име; валидна заявка без токен връща 303 и се записва; honeypot се отхвърля; невалиден подаден токен се маркира; над лимита се връща 429.
- Публикуването в GitHub Actions завърши успешно. На живия `https://vamo.bg/kontakt.php` заявка без съгласие върна HTTP 422 с видима грешка и запазено име.

**Чака потвърждение от собственика:** реално запитване от живата форма и получаването му в `office@vamo.bg`, както и потвърждението до подателя при посочен имейл. Автоматичните тестове умишлено не изпращаха реални писма.

## При бъдеща промяна

Проверете едновременно Astro формата и PHP формата за повторен опит: имената и задължителността на полетата трябва да съвпадат. След промяна пуснете проверките по-горе и направете контролирано реално изпращане. Не връщайте липсващ клиентски токен като условие за отказ.
